# Arch AI launchers and shared mise toolchains

All mise tools have explicit defaults in `~/.config/mise/config.toml`. Their
installations are shared under `~/.local/share/mise/installs`; project `mise.toml`
files only select versions. The Epub-to-Mp3 project retains its existing pins.
A matching global/project version uses one installation.

| Tool | Global | Epub-to-Mp3 |
| --- | --- | --- |
| Node | 26.13.0 | 26.13.0, same installation |
| npm | 12.2.2 | 12.2.2, same installation |
| Python | 3.12.10 | 3.14.10 |
| Ruby | 4.0.7 | 4.0.7, same installation |
| Codex | native 0.166.0 | npm distribution 0.167.0 |

Python 3.12.10 preserves the base interpreter used by existing virtual
environments. Ruby 4.0.7 is shared by the global environment and Epub; landingPagePietro's
legacy Ruby pin is migrated separately before removing its old installation. Other installed
mise tools use one retained version selected globally. Historical Epub worktrees
can still request older versions; explicitly install their requirements when
returning to that historical checkout. Do not change their source pins as part
of host cleanup. Independently managed system, uv and Hermes runtimes are outside
this cleanup.

Linux `.zshenv` puts stable mise shims on PATH in interactive and noninteractive
shells, removes inherited version-specific mise paths and preserves an active
virtual environment. NVM/rbenv remain fallbacks only on hosts without mise.
Reload `.zshrc` or open a new terminal after deployment.

`ai-memory run codex --yolo --jail` uses the selected mise Codex version. The
resolver accepts only native executables in that selected installation and
refuses a missing npm platform package instead of falling back to another
version. The jail maps that native executable and its available companions
read-only to stable entry points. Tiny host-side companion launchers ensure
mount targets exist even when the entire bin directory is shared read-only.
No additional Codex binaries are copied into `~/.local/bin`.

A launch from home uses `~/workspace/homelab`, scoped to `default/pips`. The
shell directory stays unchanged; this is a dedicated project, **not access to the
whole home**. Existing projects retain their own directory and memory scope.
Use a project-local launch or explicitly approved mounts for other files.

Verified user releases of ai-memory 3.4.5 and ai-jail 3.3.1 remain selected until
`/usr/bin` has an equal or newer version, then the wrappers use the system
package. ai-jail's trust-store boundary and the existing Arch `agent-guard`
resource limits remain enforced. The user-service override selects the same
ai-memory release as the CLI.

Install the global mise configuration and selected Codex before running
`bash scripts/install-ai-tools.sh`. This Linux x86_64 installer validates release
checksums, keeps rollback copies and requires the existing Arch agent-guard.
It installs only stable launcher scripts for Codex, resolving binaries through
mise. Apply the service drop-in separately; the installer never restarts services.
Machine-specific launchers/configuration are excluded from non-Linux hosts.

Validation: `python3 -m unittest discover -s tests`, shell syntax checks, then
real commands in home, a clean directory, Epub and a nested Epub directory.
Check both native and jailed Codex versions against the active mise selection.
No model prompt is needed for version, isolation or exit-status probes.

## macOS: updateAll and Brew

`updateAll` / `updateBrewBinaryOnly` updates ai-memory from the official
`akitaonrails/tap` archive. ai-jail uses a generated local tap
`pietro1704/ai-tools-local`: each run checks the latest stable GitHub release,
prefers an official Mac archive, and falls back to the tagged source on Intel.
The source archive is SHA256-pinned in the generated formula. This does not
modify the upstream tap, and `brew update` does not overwrite the local fallback.
The local tap is regenerated by the updater; `brew upgrade` alone does not discover
new ai-jail versions in it. Run `updateAll` or `updateAiToolsBrew` for that.

ai-jail uses existing Homebrew Rust >= 1.97.1, locked dependencies, two jobs,
and at least 8 GiB free. No Android SDKs or extra Rust toolchains are installed.
`updateAll` asks at startup `Permitir compilações no final? [s/N]`; only an
explicit yes enables the final source queue. `updateAll --allow-compile`
enables it without a prompt. Noninteractive execution defaults to no builds.
Brew/MacPorts applications lacking current compatible binaries are retried
individually in the final queue. A failed app is reported and the next is tried;
Ctrl-C cancels. The final compilation stage releases existing pins before processing dependencies.
No new pins are created. All Brew formulas, including previous source exclusions,
participate in the opted-in queue. The separate Herdr/Hermes launchers are not
invoked by this package-manager phase.
Each build checks 8 GiB free and uses two jobs. No caches or data are deleted by
this queue; toolchain/platform errors are reported rather than overriding pins.
All ordinary updates run before the source queue.

Load `source ~/.local/lib/package-updates/binary-updates.zsh`, then use
`updateAiToolsBrew --dry-run` to inspect or `updateAiToolsBrew` to update binaries
for only these two tools. `updateAiToolsBrew --allow-compile` also allows the
ai-jail fallback. `updateAll` defers that fallback to its final source queue.
Old standalone executables
are backed up under `~/.local/state/ai-tools-migration-*` and atomically replaced
by symlinks to Brew's stable `opt` paths, preserving absolute-path integrations.
Configurations, hooks, data stores and service definitions are left intact.
Running servers need a separate controlled restart to load the new executable.

`updateAll --dry-run` plans package updates without running installers,
changing pins, or compiling. Add `--allow-compile` to include the final source
queue and planned pin removal. The final read-only inventory checks every
installed Brew formula/cask, MacPorts updates, and stable AI release versions.
Pending updates or a failed inventory return nonzero and suppress the completion
message. A dry run reports the current state; it cannot prove that compilation
will succeed. Brew/MacPorts metadata is read from current local catalogs.

Prefer compatible prebuilt archives, including MacPorts, before compilation.
MacPorts' binary-only updater runs before Brew's binary-only phase. A MacPorts
archive cannot replace a Homebrew library in place: cross-manager migration
requires checking the installed dependents and command/configuration paths.

For independent CLI apps, the binary stage probes official MacPorts archive and
signature URLs for this host, requires the same upstream version, and checks
Brew reverse dependencies and executable identity. It uses `port -b` so missing
binary dependencies cannot trigger compilation. Only after installation and
version verification does it back up and remove the obsolete Brew app; stable
absolute command paths are preserved. Configuration files are not touched.
Shared libraries, service managers and shadowed standalone installations remain
under their existing manager. A package that remains installed in Brew is still
audited and may require a Brew-compatible build despite a MacPorts library archive.
